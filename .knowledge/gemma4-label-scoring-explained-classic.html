clipCC · Technical Note · Gemma 4 E2B

How Gemma decides
the best-fitted label

A generative vision-language model doesn't measure your labels against the video. It looks at the frames and writes down a score for each. This note traces that calculation, end to end.

google/gemma-4-E2B-it semantics: verbalized · uncalibrated endpoint: /api/v1/gemma/label_scores
The one thing to remember

The “best-fitted” label is simply the one Gemma assigns the highest number to — and that number is text the model generated, not a similarity it computed. There is no embedding distance, no softmax, no probability. Eight frames go in; a small JSON array of self-reported 0 – 1 scores comes out; the label with the largest score wins.

01

Two very different ways to score

clipCC ships two models on two pages. They answer the same question — “how well does this label fit?” — with completely different machinery. Knowing which one you're on changes how you read the numbers.

/ · the SigLIP2 page

It measures

  • Encodes the image and the text into vectors, then takes their similarity.
  • A sigmoid turns that similarity into a 0 – 1 score, independently per label.
  • Scores are a real, repeatable computation over embeddings.
  • Calibrated enough to compare across runs; threshold at 0.5.
/gemma · this page

It reads & reports

  • Sees the actual frames plus your labels as one prompt.
  • Generates a JSON array — it literally writes a number for each label.
  • The score is a verbalized self-report: judgment, not arithmetic.
  • Uncalibrated & quantized to round numbers. Read it as a ranking, not a probability.
✦
Because the score is generated text, the whole “calculation” is really a prompt + a decode loop + a strict parser. The next section walks every stage of it.
02

The calculation, stage by stage

One request to POST /api/v1/gemma/label_scores (a video + a JSON list of labels + an optional window start) flows through seven stages. The model must be warmed first — it loads once, on demand, and stays resident.

1

Admit & guard the request

Two checkpoints, in order. Before any video work: the extension, the label list, and the slot state are checked — the slot must already be loaded or the call is refused with 503. Then the upload is saved and probed with ffprobe, and only now are duration, resolution, and stream count validated.

up-front: ext ∈ mp4·avi·mov·mkv up-front: labels 1–50, non-empty, unique up-front: slot loaded (else 503) after probe: duration ≤ 300s after probe: ≤ 3840×2160 & ≤ 8.3MP after probe: single video stream

Why: Gemma samples a fixed number of frames from a window, so the usual “frames-vs-duration” rule is skipped — only the hard safety limits apply. Note the file is accepted and probed before the resolution/duration verdict, not gated ahead of upload.

2

Choose the analysis window

Gemma never looks at the whole video. It analyzes a single 60-second window that begins at the window_start you provide (default 0), clamped to the video's end.

window = [ window_start , min(duration, window_start + 60) ]
window_start must be ≥ 0 and < duration length = gemma_analysis_window_seconds = 60.0

Why: A VLM has a finite image budget. A bounded window keeps the frame set small, sharp, and within the prompt — and lets you aim the analysis at the part of the clip you care about.

3

Plan the frame timestamps

The window is cut into N equal slices and one frame is taken from the midpoint of each. By default N = 8. A 0.5 s spacing floor collapses N on very short windows so two frames are never visually redundant.

N = min(Nmax, max(1, ⌊span / 0.5⌋))  ·  tᵢ = window_start + (i + 0.5) · span/N
frames = effective_gemma_max_frames = min(8, 16) spacing floor = 0.5s timestamps rounded to 3 dp

Why: Uniform midpoint sampling gives even, deterministic coverage of the window. These exact timestamps are the closed set the model is told it is seeing, in order.

4

Extract & downscale the frames

One fast ffmpeg seek per timestamp (-ss before -i) grabs a single frame, downscaled so its longest side is at most 896 px with aspect ratio preserved, saved as high-quality JPEG.

scale min(896, iw/ih), keep aspect JPEG -q:v 2 per-seek timeout 120s

Why: The 896 px ceiling is a hard-coded ffmpeg scale filter — large enough to read behavior, small enough for the vision encoder. It is what actually bounds image size today; the gemma_image_token_budget setting is not yet wired into the processor. No frames extracted → the request fails fast.

5

Build the scoring prompt

Your labels are numbered 1…N and dropped into a fixed instruction that demands a strict JSON array — one object per id, each with a score from 0.0 to 1.0. The prompt also asks the model to add a one-sentence evidence note to its k highest-scored labels — a request, not a step the system enforces.

question per label: “how strongly is this visible anywhere in the frames?” evidence on top k = 3 (model-requested) token budget = min(64 + 24·N, 1280)

Why: Numbering by id (not by text) makes the output order-independent and unambiguous to parse, and lets the parser reject anything that doesn't map back to a real label.

6

Generate the scores

The frames (as images) and the prompt go in as a single multimodal turn. Gemma decodes the answer greedily — no sampling — so the same input gives the same scores. This decode loop is the calculation.

do_sample = False (deterministic) enable_thinking = False (chat template) dtype bf16 on GPU/MPS · fp32 on CPU max_new_tokens = budget

Why: Greedy decoding makes results reproducible. The “thinking channel” is disabled because its stray tokens would corrupt the JSON. The request timeout is soft — checked between tokens — so max_new_tokens is the real bound.

7

Parse, validate, and rank

The text is stripped of code fences, sliced to the outermost [ … ], and parsed strictly. Each item must be an object with a known, unique id and a numeric score in range. A bad parse triggers exactly one retry; a second failure is an error.

reject: unknown id · duplicate id · non-numeric / out-of-range score missing id → score = null (shown “n/a”) retries = 0 or 1

Why: Scores return in your original label order. The best-fitted label is the one with the highest score — picked by you from the ranked list, since the scores are independent and need not sum to anything.

03

A worked example

A 90-second dashcam clip. You set window_start = 10 and submit three labels. Here is exactly what the system computes.

Input

video duration 90s · window_start 10 · labels ["texting while driving", "sleeping while driving", "eating while driving"]

Stage 2 — window

[ 10 , min(90, 10+60) ] = [10s, 70s]  →  span = 60s

Stage 3 — 8 midpoint timestamps (slice = 60/8 = 7.5s)
f0 13.75s f1 21.25s f2 28.75s f3 36.25s f4 43.75s f5 51.25s f6 58.75s f7 66.25s
Stage 5 — the prompt Gemma receives (with the 8 frames)
You are analyzing frames sampled from a video, in chronological order.
Score how strongly each numbered behavior below is visible anywhere in these frames.

Behaviors:
1: texting while driving
2: sleeping while driving
3: eating while driving

Respond with ONLY a JSON array, no other text. One object per behavior id:
[{"id": <behavior number>, "score": <number from 0.0 to 1.0>}]
For the 3 highest-scoring behaviors only, add an "evidence" field: one short sentence...
Scores must be JSON numbers, not strings. Include every id exactly once.
Stage 6 — what the model writes back
[{"id": 1, "score": 0.8, "evidence": "The driver holds a phone in their right hand near the wheel."},
 {"id": 2, "score": 0.1},
 {"id": 3, "score": 0.0}]
Stage 7 — parsed, ranked, rendered

0.80

“The driver holds a phone in their right hand near the wheel.”

sleeping
0.10

0.00

Best-fitted label = “texting while driving” — it carries the largest generated score. Note the scores total 0.9, not 1.0: each is judged on its own.

04

What the winning score actually means

The bar that fills the most is the answer — but read it for what it is.

It's a ranking signal, not a probability. The model is asked to rate each behavior independently (“how strongly is each visible”), so the scores don't form a distribution and won't sum to 1. Two labels can both read 0.8; none has to.

It's quantized and uncalibrated. Generative models gravitate to round numbers — 0.0, 0.5, 0.8 — so treat the values as ordinal: higher beats lower, but the gap between 0.7 and 0.8 isn't a precise 0.1 of anything. And a Gemma 0.8 is not comparable in magnitude to a SigLIP2 0.8.

It's implicitly contrastive. Even though each label is rated on its own, the model sees all of them at once in one prompt, so its scores are quietly relative to the set you submitted. Change the label list and the numbers can shift.

Score semantics — gemma4_verbalized_uncalibrated
Scores are verbalized self-reports from a generative model: uncalibrated, quantized to round numbers, and implicitly contrastive across labels. Treat as ordinal. NOT comparable in magnitude to SigLIP2 sigmoid scores. Not suitable for safety-critical decisions.

06

Good to know at the edges

SituationWhat happens
Model omits a label idThat label's score becomes null and renders as n/a — not zero.
Very short windowThe 0.5 s spacing floor caps N below 8 (e.g. a 3 s window yields 6 frames), so you never get redundant near-identical frames.
Malformed JSON from the modelProse around the array is tolerated (sliced to the brackets); a genuinely bad parse buys exactly one regeneration, then a 502 (“Gemma output unusable”).
Window past the clip endwindow_start ≥ duration is rejected as invalid before any work starts.
Slot not warmedScoring calls return 503 until POST /api/v1/gemma/warm finishes loading (~minutes on first run; load-once, then resident).
Request runs longThe timeout is a soft deadline checked between decode steps; the response carries per-stage latency and the retry count.
